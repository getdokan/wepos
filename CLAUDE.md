## Commands

```bash
npm run build      # production bundles (runs both webpack configs)
npm start          # webpack dev server on :8887, hot reload
composer phpcs     # WPCS lint; composer phpcbf to autofix
npm run makepot    # regenerate languages/wepos.pot
npm run release    # prod composer install + mozart + build + pot + version-replace + zip
```

`npm run build` must be run before the plugin works from a clean checkout — `build/` and `assets/js|css` are gitignored.

### Tests (Playwright, in `tests/pw`, uses pnpm)

```bash
cd tests/pw
pnpm install:dev && pnpm pw:chrome-only   # deps + chromium
cp .env.example .env                      # credentials, BASE_URL, WEPOS_PRO flag
pnpm start:env                            # wp-env on :9999, mounts the repo root as the plugin
pnpm test:api                             # api_tests project (api.config.ts)
pnpm test:e2e                             # e2e_tests project (e2e.config.ts)
pnpm test:e2e:lite                        # only @lite-tagged specs
npx playwright test tests/e2e/<file>.spec.ts --config=e2e.config.ts   # one file
npx playwright test --config=e2e.config.ts -g "<test title>"          # one test
pnpm test:debug / pnpm test:report / pnpm lint / pnpm prettier
```

Specs are tagged `@lite`, `@pro`, `@liteOnly`, `@core`, `@visual`, `@exploratory` and the npm scripts grep on those tags. The plugin must be built before starting wp-env, since wp-env installs `../../` (the repo root) as the plugin.

## Architecture

### PHP layer

`wepos.php` is a singleton (`wepos()`) holding a `$container` array; every subsystem is instantiated in `init_classes()` and reachable as `wepos()->admin`, `wepos()->rest`, etc. Classes live in `includes/` under `WeDevs\WePOS\` (PSR-4). `dependencies/` holds Mozart-prefixed vendor code (Appsero) generated by `composer install` — never edit it by hand.

REST controllers live in `includes/REST/`, are registered by `REST\Manager`, use namespace `wepos/v1`, and mostly extend WooCommerce's own controllers. `includes/Dokan.php` is the marketplace integration: it hooks `wepos_frontend_permissions`, `wepos_rest_*`, and `dokan_*` filters so each vendor sees only their own data.

### Two UI generations coexist

Legacy Vue 2 (`assets/src/`) and React 18 (`src/`) both ship. The `wepos_appearance` option decides which renders:

- `admin_ui_style` — `new` → React admin (`src/admin`), `legacy` → Vue admin (`assets/src/admin`)
- `pos_layout_style` — `latest` → React POS (`src/frontend`), `legacy` → Vue POS

`wepos.php` picks `Assets` (Vue stack) or `ReactAssets` (React stack) accordingly. New work goes in `src/`; touch `assets/src/` only for legacy-path bugs.

### Bundling: carrier + main

`webpack.config.js` exports **two** configs:

1. **carrier** — `wepos-components` (`src/index.ts`) bundles `@wedevs/plugin-ui` and `react-router-dom` once and publishes them on `window.__weposPluginUI` / `window.__weposReactRouterDOM`.
2. **main** — every other entry (`wepos-react`, `wepos-admin-react`, `wepos-appearance`, plus the legacy Vue bundles) externalizes those two packages to the globals above. wepos-pro uses the same pattern.

React entries emit unhashed files into `build/`; legacy Vue entries emit into `assets/js` and `assets/css` with a `.min` suffix in production. Adding a React entry means editing both the webpack entry list and the PHP enqueue in `ReactAssets.php`.

**Dev mode is detected by file existence**: if `build/runtime.asset.php` exists (only while `npm start` runs), PHP loads scripts from `http://localhost:8887` instead of `build/`. A stale `runtime.asset.php` will break the admin after the dev server stops.

### React admin: Shadow DOM + hash routing

`src/admin/index.tsx` mounts into `#wepos-admin-react-app` inside a **Shadow DOM** (`src/components/ShadowContainer.tsx`), with stylesheets injected as `<link>` from `weposAdmin.adminCssUrls`. Consequences:

- `document.querySelector` from the page will not find app nodes — query through `host.shadowRoot`.
- Tailwind v4 (`src/admin/styles/main.css`) is scoped to `.pui-root` and `@source`s both this repo and `../wepos-pro/src/admin`, so utilities used only in pro still get generated.
- plugin-ui portals that escape to `document.body` are intercepted and redirected into the shadow root.

All wePOS submenu items point at one admin page and navigate by hash. `Admin\Appearance::rewrite_submenu_url()` swaps `page=wepos#` ↔ `page=wepos-dashboard#` depending on `admin_ui_style`; routes that exist only in React register through the `wepos_react_only_hash_routes` filter so they always land on the React shell (see `Admin\Premium`).

### Extension points

JS hooks share one `@wordpress/hooks` instance on `window.__weposReactHooks` (`src/frontend/hooks/useExtensions.ts`), created by a PHP inline script before any bundle loads, so pro scripts can register hooks that run when the base app renders. `wepos_react_admin_routes` adds or replaces admin routes; a route's `page_key` is checked against `weposAdmin.allowed_pages` (from `wepos_get_user_allowed_pages()`, backed by `Settings\Caps`) before it is registered.

POS state uses `@wordpress/data` stores registered from `src/frontend/store/` (`cart`, `products`), not Redux or Zustand. The POS page itself is `templates/wepos.php`, swapped in by `Frontend::rewrite_templates()` on `template_redirect`.

## Conventions

- PHP: WPCS, 4 spaces, text domain `wepos`, `@since` tags on new public methods.
- **Never hardcode a version in `@since` (or `@deprecated`) tags — write the literal token `WEPOS_SINCE`**, e.g. `@since WEPOS_SINCE`. `npm run version-replace` (part of `npm run release`) rewrites every `WEPOS_SINCE` across `assets/`, `includes/`, `templates/`, `src/` and `wepos.php` to the `package.json` version, so the tag always lands on the release that actually shipped the code. A hardcoded `@since 1.5.0` survives the replace and goes stale the moment the release slips.
- TS/JS in `src/`: tabs and WordPress-style spacing inside parens — this contradicts `.prettierrc` (2 spaces, no tabs), so running Prettier over these files reformats them wholesale. Match the surrounding file instead.
- Admin pages that follow a Figma design (e.g. `src/admin/pages/premium/`) hardcode the design's hex values rather than plugin-ui theme tokens; keep that split rather than mixing the two in one component.
